Build plan (reusing what's there)

  • Backend: one GET /shipping/orders/overview taking the list's filters (channels, countries, from, to) and returning counts, daily series, spend by carrier and attention counts, so the cards load together and share filters.
  • API slice: useGetOrdersOverviewQuery in services/api/shipping.api.ts, beside useGetChannelOrdersQuery.
  • Feature: features/shipping/orders/overview/ with OverviewTab and small pure cards (PipelineCard, AttentionCard, SpendCard, OrdersPerDayCard) so one failing card doesn't block the rest.
  • Reuse: KpiCard, FilterBar + useStagedFilters, DateRangePicker, StatusBadge, ChannelBadge, EmptyState, design-system/charts, FULFILLMENT_META, STATUS_TONE.
  • Routing: tab in the address (?tab=overview|orders), like the booking drawer's ?shipment=. KPI clicks write ?tab=orders&states=…; OrdersScreen reads states as initial filter, as it already does for search.
  • Permissions: reuse shipping:orders; no new subject.

Decisions for you

  • Tabs (Overview | Orders) as drawn, or the KPI strip above the existing list on one page?
  • Overview as the default landing, or keep landing on the list?
  • Is on-time % needed in v1 (needs delivery-date data)?
  • Can we store a promised ship-by date from Amazon / Walmart for an "Overdue" KPI?

Beddora · Shipping › Orders · Bulk rates & bulk book6 / 6 · Rules and build map

Rules

TopicBehaviour
Who can be selectedTo Book channel orders only (manual shipments and drafts keep their own flow). Needs shipping:orders write; without it no checkboxes show.
Selection sizePage or "all matching filters", capped (proposed 50 per batch) with a clear message above that.
ReviewSame checks the single flow makes (mapped SKUs, ship-to, package, customs). Blocked orders are listed with the fix link and skipped unless fixed; they never block the rest.
RatesFetched per order over the existing rate stream, a few at a time. Rows fill in as they arrive. "Pick for all" uses the existing Cheapest / Fastest / Best value tags; manual picks stick.
BookingOne booking job per order, each with its own idempotency key, so a retry or double click can't buy a label twice. Partial success is normal: booked rows stay booked, failed rows are retried alone.
Leaving the pageJobs run server side. Back in Orders the rows show Booking / Booked, and the realtime stream updates them.
MoneyThe Confirm step is the only point that spends. It shows the total and per-carrier split; the button names the amount.

Built from what exists

  • Reuse: useRateStream, rateRanking (tags and sorting), RateRow text and CarrierLogo, useStartBookingMutation + useBookingJob (realtime shipping.booking), valuesFromOrder and unmappedLines (readiness), PrintDialog, WizardStepper, FilterBar, SearchableSelect, StatusBadge.
  • New screen: features/shipping/orders/bulk/ with BulkBookScreen and a small state hook that holds the selected orders, each row's quoted rates and chosen rate; one row component per step.
  • Orders list: a checkbox column, header checkbox, and the selection bar; selection kept in the address or session storage so Back from the bulk page restores it.
  • Route: /dashboard/shipping/orders/bulk.

Backend needs

  • CHECK Today's rates and booking are per order. Looping them from the browser works for small batches; for 50 orders a batch endpoint (create batch, then realtime per-order results) is safer, runs when the tab closes, and enforces the cap.
  • CHECK How long a quoted rate stays valid; if short, Confirm must re-quote rows older than that before booking.
  • CHECK Carrier rate-limits for many parallel quotes (decides the concurrency).

Decisions for you

  • Cap per batch (50?) and whether "select all matching filters" is allowed.
  • Skip blocked orders automatically, or stop and make the user fix them first?
  • Should "Pick for all" remember the last rule per user?
  • Batch endpoint now, or ship the browser-side loop first?

Beddora · Shipping › Orders · Bulk labels, tracking & cancel5 / 5 · Rules and build map

Rules

ActionBehaviour
Entry pointOne "Bulk actions" menu in the selection bar. Each item shows n of selected it can act on; ineligible orders are skipped and listed with the reason before anything runs.
Print labelsNeeds a booking with a label (not channel-shipped, not voided). Same format choices as today's Print dialog, limited to formats all selected carriers offer; "Remember my choice" shared. PDF: one merged file in a new tab. ZPL: one combined .zpl download.
Commercial invoicesOnly cross-border parcels that have one; others skipped.
Refresh trackingPer parcel, a few at a time, with a progress count. Safe to repeat. Statuses already come from carrier scans; this just pulls them now.
Cancel / voidOnly unscanned labels. Shows the refund total, needs typing VOID from 5 labels up, voids each parcel on its own and reports Voided / Void pending / Failed. Failed rows can be retried alone.
PermissionsPrint and tracking need read; cancel needs shipping:orders write.

What exists, what's new

  • Reuse: PrintDialog shell (RadioCards, useLabelFormats, remembered format), usePrintDocument, CancelShipmentDialog wording and ConfirmDialog, useRefreshTrackingMutation, TrackingTimeline, STATUS_TONE, the Orders table and the selection bar from the bulk-booking design.
  • New UI: BulkPrintDialog, BulkCancelDialog, BulkTrackingDrawer, plus Tracking status and Carrier filters on Orders.

Backend needs

  • NEW Merged labels: the app has no PDF-merge or zip package, and the labels are fetched one by one today. Merging is best done on the server: POST /shipping/shipments/documents/bulk returns one PDF (or one ZPL).
  • HAVE Void and refresh tracking exist per shipment (/cancel, /tracking/refresh); looping them from the browser works for small batches. A bulk endpoint is better beyond about 20.
  • CHECK The orders list can't filter by tracking status or carrier yet.
  • CHECK What an order becomes after its label is voided (back to To Book so it can be rebooked, or Cancelled)? Not clear from the frontend.

Decisions for you

  • Merged PDF in one tab, or a downloaded file?
  • Threshold for typing VOID (5?), and a cap on bulk size (50?).
  • Is the tracking roll-up drawer needed in v1, or are the new filters and Refresh tracking enough?
