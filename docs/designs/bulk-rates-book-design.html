Beddora · Shipping › Orders · Bulk rates & bulk book6 / 6 · Rules and build map

Rules

TopicBehaviour
Who can be selectedTo Book channel orders only (manual shipments and drafts keep their own flow). Needs shipping:orders write; without it no checkboxes show.
Selection sizePage or "all matching filters", capped (proposed 50 per batch) with a clear message above that.
ReviewSame checks the single flow makes (mapped SKUs, ship-to, package, customs). Blocked orders are listed with the fix link and skipped unless fixed; they never block the rest.
RatesFetched per order over the existing rate stream, a few at a time. Rows fill in as they arrive. "Pick for all" uses the existing Cheapest / Fastest / Best value tags; manual picks stick.
BookingOne booking job per order, each with its own idempotency key, so a retry or double click can't buy a label twice. Partial success is normal: booked rows stay booked, failed rows are retried alone.
Leaving the pageJobs run server side. Back in Orders the rows show Booking / Booked, and the realtime stream updates them.
MoneyThe Confirm step is the only point that spends. It shows the total and per-carrier split; the button names the amount.

Built from what exists

  • Reuse: useRateStream, rateRanking (tags and sorting), RateRow text and CarrierLogo, useStartBookingMutation + useBookingJob (realtime shipping.booking), valuesFromOrder and unmappedLines (readiness), PrintDialog, WizardStepper, FilterBar, SearchableSelect, StatusBadge.
  • New screen: features/shipping/orders/bulk/ with BulkBookScreen and a small state hook that holds the selected orders, each row's quoted rates and chosen rate; one row component per step.
  • Orders list: a checkbox column, header checkbox, and the selection bar; selection kept in the address or session storage so Back from the bulk page restores it.
  • Route: /dashboard/shipping/orders/bulk.

Backend needs

  • CHECK Today's rates and booking are per order. Looping them from the browser works for small batches; for 50 orders a batch endpoint (create batch, then realtime per-order results) is safer, runs when the tab closes, and enforces the cap.
  • CHECK How long a quoted rate stays valid; if short, Confirm must re-quote rows older than that before booking.
  • CHECK Carrier rate-limits for many parallel quotes (decides the concurrency).

Decisions for you

  • Cap per batch (50?) and whether "select all matching filters" is allowed.
  • Skip blocked orders automatically, or stop and make the user fix them first?
  • Should "Pick for all" remember the last rule per user?
  • Batch endpoint now, or ship the browser-side loop first?
