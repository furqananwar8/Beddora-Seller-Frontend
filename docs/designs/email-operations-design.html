Design proposal · 3 of 3

How it works, live updates, and what changes in the system

Most of it reuses what exists: every email is already a stored row with a status, each event already builds its own email, and the app already has an SSE channel.

What already exists ✓

  • Every email stored as a row: QUEUED / SENT / FAILED, tries, last error, created and sent time.
  • Queue with automatic retries (8 tries, about 20 minutes), sending 2 at a time.
  • A duplicate guard per person and record, so nothing is sent twice by accident.
  • Each event (PO approved, container delivered, …) builds its email from just a record id.
  • The SSE hub and topic registry used by Finance and Procurement screens.

What is new

  • Screen System › Email: list, tabs, search, selection and bulk actions.
  • Delivery history a new table, one line per try (time, sent or failed, error, automatic or resent by whom). Today only a counter is kept, with no timestamps, so history starts from this release.
  • Resend one or many, any status, adding to the history. Sent emails ask for a confirmation first.
  • Existing data pick events and a date range, preview, send. Same emails, email only, duplicates skipped.
  • Access Furqan, Fahad, Radhika and Salman only, kept out of the permission dialog. Everyone else: no menu item, 403 on the API and on the live channel.

Live updates (SSE)

Worker sends or fails→Saved with history→Event on topic system.email→Screen updates
  • Events: queued, sent, failed, resent. Each carries the email id, new status, times sent, last time and last error.
  • On the screen: the row is patched in place (no reload), the tab and box counts move, the row flashes briefly, and a toast says what happened: “Email sent · PO-1128, to buyer.one@company.com” or “Email failed · … · Connection timeout”.
  • Bulk: many events in a short burst become one summary toast, e.g. “12 emails sent, 2 failed”, so 43 emails don't throw 43 toasts.
  • Filters respected: a row only appears or leaves the list if it matches the current tab and filters; the counts always update.
  • If the connection drops: the screen shows “reconnecting” and reloads once when it is back, so nothing is missed. The “Live” tag turns grey while offline.
  • Open history window: a new try adds its line by itself.
  • Who receives it: only the four allowed accounts, checked when they subscribe.

Limits to know

  • Old records are emailed from their current state and the event's current wording.
  • Recipients come from today's Notifications settings for that event; the person who originally acted is not excluded.
  • History before this release can't be recovered. Bulk actions are capped at 200 rows per click.

Please confirm

  • 1. Resending an email that was already sent: allowed, with a confirmation, and the history shows each send. OK?
  • 2. Old records: email only (no bell notifications). OK?
  • 3. Which events: PO approved and rejected, container delivered, payment request approved, price analysis approved, shipment confirmed, shipping booked, plus the ETA and ETD reminders. Add or remove any?
  • 4. Menu name: “System” is a placeholder for the new sidebar group. What should it be called?
