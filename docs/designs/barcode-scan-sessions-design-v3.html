How a scan session works

The same lifecycle for Shipments, Shipping orders and Inbound receiving. Only the inventory direction differs.

1

Start

Scan items opens with the expected SKUs and counts already known. A session row is created with its source and channel.

2

Scan

Each UPC is pushed to Redis the moment it is scanned, so fast scanning never waits on the database.

3

Match in batches

Queued UPCs are looked up against product UPCs in batches. Matched UPCs group under their SKU; the rest show as Not matched, with the reason.

4

Confirm

End session, or the ×, always asks first and shows what will change in inventory.

5

Sellable or damaged

Inventory in only: asked once, here, per product. The rest are sellable.

6

Come back or close

Not closed: start again for what is missing. Closed: no more scanning on that record.

Where it shows
Shipments row action · Shipping › Orders row action (channel orders only) · Inbound receiving screen. The Scanning Sessions listing shows the same name in a Started by column, and the detail page keeps it afterwards.
1Start: try to take the lock scan-lock:shipment:19 in one atomic step, only if it is free, with a 90 second life. It holds the session ID, user ID and name. If it is taken, the button shows who has it.
2While scanning: the open modal renews the lock every 30 seconds. A closed tab or lost connection stops the renewals and the lock expires on its own.
3End session: release the lock only if it is still yours, then save. Release comes after the inventory update, so nobody can start a new session before the first one is saved.
4Backstop: the session table has a unique rule of one open session per shipment, order or receiving, so a Redis hiccup can never create two.
5Close scanning NEW: one row per record and direction (scan_closures). The server refuses to start a session on a closed record.
