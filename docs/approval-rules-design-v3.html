Behavior

  • A department can have several heads. Pick them from all active users; a head is added as a member automatically.
  • A user can be in several departments.
  • A department can be marked as the team for one product platform (Retail or Ecommerce). Rules use this to pick approvers from what is on the PO.

  • Deleting a department that a rule uses is blocked, with a list of the rules.
  • Changing the heads shows a warning: "3 approval rules use this department."
  • A department with no heads shows a red No head badge, and rules using it cannot be saved.

What is on screen

  • 1Action list comes from code: one entry per button that supports approval. Shows how many steps each has.
  • 2Several people per step. Add as many chips as needed: a department's head, or any user (e.g. a second person from the same department, or people from different departments).
  • 3"Move on when" (per step). Everyone in the step is notified together. Any one approves (default): the first approval moves on, others are told it's handled. Everyone approves: moves on only after all have approved. One from each team: each chip is a team, and every team needs one approval from its own people. In every mode a rejection by anyone ends the chain.

  • 5Fixed outcome: the last approval triggers the action's own result (for a PO: approved and locked).

Checks on Save (errors shown inline)
  • Every step has at least one person
  • Every department chip has at least one head
  • Every person is active
  • Each person holds the action's permission (e.g. po-approval.write)
  • A person listed twice in one step is merged into one

Runtime flow · one PO, step by step

Who does what when you click Submit. Dashed red lines are rejections.

Atomic decisions. Approving closes the task with UPDATE … WHERE status='PENDING' in a transaction, the same guard the PO uses today, so a double click or two tabs can never advance the chain twice.
Stateless handler. It only ever asks: "which step am I on, and is there a next one?" The steps were copied at submit, so nothing re-reads a rule mid-flight.
Several people in a step. Each "notify" above opens one task per person in that step, all notified together. Any one approves: the first approval closes the others ("handled by Khanjan") and advances. Everyone approves: advances only when the last open task is approved. In both modes a rejection by anyone ends the chain.
Step 3 repeats for however many steps the rule has5

Data and handler additive only

Six new tables. Nothing existing is renamed or removed. Names illustrative; final ones follow schema.prisma conventions.

// who sits where
model Department       { id, name }
model DepartmentMember { userId, departmentId,
                         isHead Boolean }   @@unique both; many heads ok

// admin-edited rule: one per action
model ApprovalRule {
  actionKey String @unique   // 'procurement.po.submit'
  isActive  Boolean
  steps     ApprovalRuleStep[]
}
model ApprovalRuleStep {
  ruleId, position Int
  completion ANY | ALL   // default ANY: one approval / all must
}
model ApprovalRuleStepAssignee {  // many per step
  stepId
  departmentId Int?   // all its heads, OR
  userId       Int?   // a named person (exactly one set)
}
// per submitted document (runtime)
model ApprovalTask {          // one per person per step
  actionKey, entityId
  position Int  totalSteps Int  completion ANY|ALL // copied at submit
  assigneeId Int        // resolved when the step opened
  status PENDING|APPROVED|REJECTED|SKIPPED|CANCELLED
  note, decidedAt, createdAt
}

The action registry (code, not database)

// one entry per button that supports approval
registerApprovalAction({
  key: 'procurement.po.submit',
  label: 'PO · Submit',
  permission: 'procurement.po-approval.write',
  onApproved: (id, actor) => po.approve(id, actor),
  onRejected: (id, actor, why) => po.reject(id, actor, why),
  describe: (id) => poSummary(id),   // for notifications
})

Handler, in plain words

start(key, id):  rule = rules[key]; if none → legacy path
              open step 1 = one task per person → notify all
decide(task, ok): close task atomically
   reject  → cancel siblings, onRejected(...) · stop
   approve → ANY: cancel siblings, step done
             ALL: step done only if no sibling PENDING
   step done → next step ? open its tasks, notify all
                         : onApproved(...)
Existing codeWhat changes
po.service.submit / createAfter setting PENDING_APPROVAL, call approvals.start('procurement.po.submit', id).
po.service.decideReject with a clear 403 unless the user holds the open task; then call approvals.decide. Legacy check remains when no rule.
procurement.notifications.tspoApprovers() becomes the no-rule fallback. A generic "task assigned" rule notifies each assignee of the open step.

How actions are wired, and what admins can change

Two kinds of things with different owners. Actions need code (a developer wires a button once). Departments and rules are data (admins change them on screen, no deploy).

Developers own: actions

  • The list of approvable buttons ("PO · Submit", "Invoice · Submit"…)
  • The API each button calls
  • What "approved" and "rejected" do to the record
  • Which events exist (e.g. "container delivered")
Changes only through code. Shown to admins as a read-only list on the Approval rules screen.

Admins own: departments and rules

  • Add, rename, remove departments; set heads and members
  • Build each action's chain: steps, people, "Any one" / "Everyone"
  • Choose who is told after each event, by bell and email
  • Change any of it later, with no deploy
Stored in the database. Applies to new submissions immediately.
How a button reaches its rule

Admin adds a department no code

  1. Settings › Approvals › Departments › New department (or inline in the step picker), add name, heads, members.
  2. It appears in the step picker on Approval rules.
  3. Add it to any action's chain. Done.

Developer adds approval to a new button small code change

  1. Register the action (key, label, permission, onApproved, onRejected).
  2. Call approvals.start(key, id) in that button's endpoint.
  3. The action appears on Approval rules with "none" until an admin builds its chain.

Retail and Ecommerce: approvers picked by the PO's products

One rule for all POs. The rule asks "which platform are these products on?" and picks the matching team's people, so there is no separate rule per platform.

Set up once, in three steps

  1. Departments tab: create "Retail team" (heads x1, x2, x3) and "Ecommerce team" (heads y1, x1, z1). On each, set Approves products on platform to Retail or Ecommerce. A person can be in both.
  2. Approval rules tab: open PO · Submit and add a step with the chip By product platform.
  3. Set that step to One from each team. Done.

What happens on each PO

The PO containsWho is asked
Only Retail SKUsRetail team heads. Any one approves.
Only Ecommerce SKUsEcommerce team heads. Any one approves.
BothOne Retail head and one Ecommerce head must approve. Both teams are notified at the same time.
A person in both teams (x1)Their single approval covers both teams.
People are dynamic. The rule stores "Retail team", not names. Change a team's heads on the Departments tab and the next PO picks the new people automatically. POs already waiting keep who they were sent to.
Where the platform comes from: every product has a platform (PoProduct.platform: ECOMMERCE or RETAIL), chosen per variation. A PO line can only be a variation or a master without variations, so each line's own platform is the one used. Looked up when the PO is submitted.
Why one rule, not two: separate "Retail PO" and "Ecommerce PO" rules cannot handle a PO with both, and double the upkeep. One rule with the platform chip handles all three cases.

Edge cases

  • A team has no heads, or no team is marked for a platform on the PO: step shows stuck + admin alert, never skipped.
  • The PO is edited while pending and its platform mix changes: the step is re-resolved. Only newly needed people are notified.
  • Platform defaults to Ecommerce. A Retail product saved without changing it would route to the Ecommerce team, so review products before go-live.
  • A PO with no lines has no platform: block submit, or the step shows stuck.

Small additions to the tables

Department      + platform  PoPlatform?   // RETAIL | ECOMMERCE | none
StepAssignee    + kind BY_PLATFORM       // next to USER / DEPARTMENT
RuleStep        completion + PER_GROUP   // one per team chip
ApprovalTask    + groupKey String?       // 'RETAIL' | 'ECOMMERCE'
The same chip can serve Price analysis (the product's platform) and, later, invoices and payment requests through their PO10

What these flows ask of the engine

  • cancel: closes open tasks (withdraw, edit after approval)
  • extra outcomes: an action may declare "hold" besides approve / reject

  • pick-then-confirm payload: step 1 chooses a supplier, later steps confirm (price analysis only)
  • Reject always lands where today's code puts it, because each action supplies its own onRejected

  • Each action's status machine and timeline (po.workflow.ts, pi.workflow.ts, payment-request transitions)
  • No rule for an action = today's behavior, so each flow can move over one at a time

1 · Purchase order approval procurement.po.submit

The flow the earlier pages used. A PO is locked as soon as it is approved.

Wired into today's code

Triggerpo.service create / update with submit, or submit(), after status = PENDING_APPROVAL
Approver todayAnyone with procurement.po-approval.write
Last approval runspo.approve: APPROVED, decidedById, approvedAt, timeline entry
Reject runspo.reject: DRAFT, reason stored, creator told

What the chain changes

  • Today every approver is told at once and any one decides. With a chain, step order and named people are explicit.
  • Resubmitting after a rejection restarts the chain from step 1.
  • Approvers can depend on the PO's products: a step can pick the Retail and/or Ecommerce team automatically (page 10).
  • Unlock-after-approval stays as it is. It is not an approval step.
Simplest fit: this is the engine's reference case. Hooks wrap the transitions already in po.workflow.ts.

2 · Purchase invoice approval procurement.purchase-invoice.submit

Invoices recorded against a PO. Approval opens the invoice for payment.

Wired into today's code

Triggerpi.service.submit: DRAFT or REJECTED to PENDING_APPROVAL
Approver todayfinance.payment-approval.write (the same permission payment requests use)
Last approval runspi.approve: PAYMENT_PENDING. Later PARTIALLY_PAID / PAID follow PO payments and are not approval
Reject runspi.reject: REJECTED with reason
Notificationspi.notifications.ts: submitted, approved, rejected, on-hold

What this flow adds to the engine

  • Withdraw (creator pulls it back) cancels the open tasks. The engine needs a cancel call.
  • Hold is a third decision besides approve and reject. An action may declare extra outcomes with their own hook (onHold).
  • Rules for invoices and payment requests are separate, even though both use one permission today.
Two actions, one permission today: after this change the permission only gates the screen. Who approves what comes from each action's rule.
Hold and withdraw are the only parts the PO flow does not already have13

4 · Price analysis approval procurement.price-analysis.approve

The one that differs most: there is no Submit button, and approval means choosing one supplier's quote.

Wired into today's code

TriggerNo submit today. "Pending" is derived: quotes exist and no supplier is approved. Proposed: starts when an analysis with quotes is saved
Approver todayprocurement.price-analysis.approval (approve) and .rejection (reject a quote)
Last approval runspa.service.approve: sets approved supplier, approver and time
Reject runspa.service.reject: marks one quote rejected; rejecting the approved quote clears the approval
EditA save that changes what an approver looked at clears approval and rejections today

Adaptations needed

  • Start automatically on save: whenever a saved analysis has at least one quote and no approved supplier, the chain starts (decided).
  • No notification spam: a save while step 1 is still waiting just updates what they see. Approvers are notified once per chain, not once per save.
  • Pick, then confirm: step 1's people choose which supplier; later steps approve or reject that choice.
  • Edit after approval cancels the running chain and starts a fresh one, mirroring how an edit clears approval today.
  • Rejecting one quote stays per quote and keeps its own permission. It also cancels any open chain.
Decided: auto-start on save. Fully automatic, no new button, and it matches today's derived "pending" status.
Fits least cleanly. Build it after the three document-style flows15

Edge cases, rollout and decisions

Edge cases decided

CaseBehavior
Creator is in a stepCreator gets no task. If that leaves the step empty, it is skipped and logged. Nobody approves their own PO.
Same person twiceWithin a step (e.g. as head and by name): one task. In a later step they already approved: auto-skipped.
Two people act at onceThe atomic update lets only one succeed. In an "Any one" step the other sees "Already handled by …"; no double advance.
Mixed modesMode is per step, so "Any one" and "Everyone" steps can be chained freely.
Department has several headsA department chip expands to all its heads. Each gets a task and a notification (bell + email). "Any one" = first head to act decides; "Everyone" = all heads must approve.
Head changed mid-flightOpen task stays with the assignee already chosen. Next steps resolve the head at that moment.
Assignee deactivatedTask shows "stuck"; admin gets an alert and a Reassign button on the task.
Rule edited / deletedPending POs keep their copied steps. Only new submissions use the new rule.
RejectPO returns to DRAFT with reason (as today). Resubmitting starts the chain from step 1.
Unlock after approvalUnchanged. Resubmitting after an edit runs the rule again.
No rule for an actionToday's behavior (all holders of the permission notified). Safe by default.
AuditEvery task keeps who, when and note; also written to the PO timeline.
