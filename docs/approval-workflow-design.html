Departments and configurable
approval workflows

Replace "notify these hardcoded people" with rules an admin edits on screen: this tab + this action goes to this person, then that person. No deploy needed to change who approves what.

The idea in one picture

Each box is a step, each arrow a route. The admin drags boxes, picks who sits in each, and saves. New POs follow the new route; POs already in flight keep the route they started with.

Short answer: is it applicable?

Yes. The app already has the three building blocks this needs: a domain-event bus, a rule-based notification layer, and an audit timeline per document. What is missing is a place to store who approves what, and an engine to walk the steps. The graph editor library (@xyflow/react) is already in package.json.

2 · The concept

Two small ideas that work together: where people sit (departments) and what happens to a document (flows).

A · Departments (the hierarchy)

  • A department has a parent, a head, and members
  • A user can belong to one or more departments
  • Optional: each user's direct manager, for "requester's manager" steps

B · Flows (the rules)

A flow is attached to a subject: one specific tab + action, for example:

procurement.purchase-order.submitPO submitted
procurement.purchase-invoice.submitInvoice submitted
finance.payment-request.submitPayment request

The flow is an ordered graph of steps. Each step says who decides (a person, a department head, "requester's manager", or anyone with a permission) and where approve and reject lead. Admins edit it on screen and publish it as a new version.

Your PO example, plus a rule you could add later

Your literal example is the straight line (Khanjan → Salman). The diamond shows that the same model supports conditions later; it is optional and does not need to ship first.

3 · Proposed schema additive only

New tables only. Nothing in users, permissions or po_orders is renamed or removed (one optional column on User).

// definition: edited by admins
model Department { id, name, parentId?, headUserId? }
model DepartmentMember { userId, departmentId, @@unique }

model ApprovalFlow {
  subjectKey  String  // 'procurement.purchase-order.submit'
  isActive    Boolean
  versions    ApprovalFlowVersion[]
}
model ApprovalFlowVersion {
  version Int; status DRAFT|PUBLISHED|ARCHIVED
  graph   Json   // editor layout (x/y), UI only
  steps   ApprovalStep[]; routes ApprovalRoute[]
}
model ApprovalStep {
  assigneeType USER|DEPARTMENT_HEAD|
               REQUESTER_MANAGER|PERMISSION
  userId? departmentId? permissionName?
  mode ANY|ALL   // one of / everyone
}
model ApprovalRoute {
  fromStepId?  toStepId?   // null to = finished
  outcome APPROVED|REJECTED
  condition Json?  priority Int
}
// runtime: one per document submission
model ApprovalInstance {
  flowVersionId; entityType; entityId
  status PENDING|APPROVED|REJECTED|CANCELLED
  currentStepId?
}
model ApprovalTask { instanceId, stepId, assigneeId,
  status PENDING|APPROVED|REJECTED|SKIPPED, note, decidedAt }

Why versions: publishing never edits a flow that has live instances. In-flight POs finish on the version they started with, which makes every past approval explainable. Why one engine: POs, invoices, payment requests and price analysis stop repeating their own decidedById pattern.

4 · How it runs, and where it plugs in

The engine is a small module under src/platform/approvals. Business modules register a subject and never contain routing logic again.

Lifecycle of one PO

#What happens
1Creator submits. po.service.submit still sets PENDING_APPROVAL as now, then calls approvals.start('procurement.purchase-order.submit', poId).
2Engine loads the active published version, creates an ApprovalInstance, resolves step 1's assignee (Khanjan) and creates an ApprovalTask.
3Engine publishes approval.task-assigned. A generic notification rule tells only Khanjan (in-app + email, deduped). Today's "tell every approver" disappears.
4Khanjan approves: task closes, engine follows the APPROVED route to step 2 and notifies Salman. Rejection takes the REJECTED route.
5Salman approves, route leads to "finished": instance = APPROVED and the subject's onApproved hook runs, which is today's approve transition (APPROVED, lock, decidedById).
6Reject at any step: onRejected hook sets DRAFT + reason, exactly as today, and the creator is notified.

Plugs into existing code

ExistingChange
po.workflow.tsKept. It stays the PO's own state machine; the engine calls its transitions.
po.service.decide()Checks "does this user hold the pending task?" instead of "do they hold po-approval.write?".
poApprovers()Becomes the fallback when no flow is configured, so nothing breaks.
NotificationRuleOne generic rule for task-assigned / decided. Per-module copies shrink.
PoOrderEventStill written; approval steps add rows like STEP_APPROVED.
SSE / realtimeEmit the existing topic events so lists refresh live.
Subject registry (strategy pattern): each tab registers { key, label, loadContext(entityId), onApproved, onRejected }. Adding invoices later means writing one registry entry, not a new engine.
Concurrency: decisions use the same guard the PO already uses: UPDATE approval_tasks … WHERE status='PENDING' inside a transaction, so a double-click or two-person step can never decide twice.
Engine owns routing; modules own what "approved" means5

5 · Step types, conditions and edge cases

Who can sit in a step

TypeMeaning
USERA named person: "Khanjan". Simple, and what you asked for.
DEPARTMENT_HEADWhoever heads Procurement today. Change the head once and every flow follows.
REQUESTER_MANAGERThe submitter's manager, resolved at runtime.
PERMISSIONAnyone holding a permission (today's behavior). Used by the legacy fallback.

mode: ANY = first person to act decides; ALL = every assignee must approve (a parallel step).

Conditions (phase 2)

A route may carry a condition on the document, e.g. { "field": "total", "op": "gt", "value": 10000 }. Each subject supplies its fields through loadContext (a PO's total is computed from lines, po-totals.ts, not stored). Conditions use a fixed JSON shape, not free-form code.

Edge cases decided up front

CaseProposed behavior
Creator is the approverStep is auto-skipped and logged, never self-approved. (Matches today's "everyone but the author".)
Assignee inactive or on leaveFalls back to the department head; if none, an admin is alerted. Optional "delegate to" per user.
Flow edited mid-flightLive instances keep their version. Admin may explicitly "re-route" one instance.
Reject destinationDefault = back to the creator (today's behavior). Option: back to previous step.
PO unlock after approvalRe-opening an approved PO starts a fresh instance on resubmit (the unlock action stays as is).
No flow configuredLegacy behavior runs unchanged. Safe by default.
Loops / dead endsPublish-time validation: every path must reach "finished" or "rejected"; no cycles in phase 1.
AuditEvery task and decision recorded: who, when, note, which flow version.
Phase 1 = linear steps. Branching and conditions are layered on the same tables later6

6 · Admin screen and permissions

Settings › Approval Flows (new)

  • Built with @xyflow/react; forms with react-hook-form + zod; success/error toasts via the existing useApiFeedback
  • Edits go into a draft version; Publish validates (no dead ends, every step has an active assignee) then activates it
  • "Test route" button: pick a sample PO and see who it would go to
  • Departments page: tree view, set head, add members

How it fits with permissions and CASL

Two separate questions, kept separate:
  • Can you see the tab? Still the existing Permission / CASL check. Unchanged.
  • Is it your turn to decide? New: an open ApprovalTask assigned to you.
Decision for you: must an assignee also hold procurement.po-approval.write?
  • Recommended: yes, validated at publish time. Keeps permissions as the safety net; a flow can't hand approval power to someone who lacks the page.
  • Alternative: the task itself grants decide-rights for that document only.
Who edits flows? A new permission pair, e.g. settings.approval-flows.write, seeded to admins. Every publish is audited.
Roles: there is no Role table today. Departments + step types cover what roles would here, so I would not introduce roles for this feature.

7 · Rollout, risks and open questions

Suggested phases

PhaseDeliversRisk
1 · FoundationDepartments + members + head. Approval tables and engine. Purchase-order flow only, linear steps, user and department-head assignees. Legacy fallback when no flow exists.low
2 · EditorAdmin graph editor, versions, publish validation, "test route", audit view.low
3 · ReachPurchase invoices, payment requests, price analysis move onto the engine. Retire duplicated approver lookups.medium
4 · SmarterConditions (amount, supplier, destination), parallel steps, delegation / out-of-office, reminders for overdue steps.medium

Risks and how they are contained

  • Approval gets stuck (assignee leaves): fallback to department head, admin alert, "re-route" action.
  • Over-engineering: phase 1 is deliberately a straight line; graph shape is in the data model but not exposed until needed.
  • Regression on the live PO flow: legacy path stays until a flow is published; engine hooks reuse today's transitions.
  • Finance's separate approver list overlaps conceptually; migrated in phase 3, not before.

Questions I need answered before building

  1. Linear or branching? Is "A then B" enough for now, or do you already need amount-based rules (e.g. only over $10,000 goes to Salman)?
  2. Rejection: back to the creator (as today), or back to the previous reviewer?
  3. One department per user, or several? (affects the member table and "department head" resolution)
  4. Assignee permissions: must they also hold the page permission (recommended), or does the flow grant it?
  5. Which tabs after PO? Invoices, payment requests, price analysis, anything else, and in what order?
  6. Absence: do you want delegation / out-of-office now, or is "falls to department head" enough?
  7. Existing approvers: on go-live, should current po-approval holders be mirrored as a single "any approver" step, or start empty?
My recommendation: approve Phase 1 + 2 for the PO flow only. It delivers exactly your Khanjan → Salman example with an editable screen, touches the live PO code in one place, and proves the engine before other modules move over.
